# Demo 单对话计时任务

更新时间：2026-09-28。本文描述 `demo-app` 当前的单次延时与固定间隔周期任务；SDK 通用持久化调度器另见 [android-scheduled-tasks.md](android-scheduled-tasks.md)。

## 目标与流程

`1.12.0 / 125` 的[演示学习手动闭环](demo-operation-learning-design.md) 与计时共用宿主忙闲边界：计时槽位 `Proposed / Waiting / Executing` 任一非 Idle 状态均阻止开始录制、试跑或再次运行，不自动取消计时；录制或操作运行持有屏幕 owner 时拒绝新的计时提案/确认、普通 Agent 和 SDK_EVENT 派发。录制暂停及最终保存仍保留占用，主界面停止可保存中断草稿；操作运行停止后先保存结果再释放占用。AI 整理本身不占屏幕。没有把已学操作接入到点执行，也没有重新启用旧 `agent_task_*` 调度器；未来定时复用路径需单独设计。

每条直接用户消息先交给当前配置的大模型作结构化意图判断。模型可提出一次性相对延时，或“每隔固定时长重复执行，直到手动停止”；宿主把模型提供的间隔、动作和重复标志交给 `demo_delay_propose` 工具，其他请求继续走原 Agent 工具循环。输入文字和助手回答都不由宿主做定时关键词、正则或格式匹配。模型路由结果缺失或无效时最多重新请求一次，仍无效则明确失败，不创建任务。App 展示任务内容、间隔与模式并要求用户明确确认；“全授权”设置不会跳过这一步。计时从确认时开始，不提前执行动作。

模型路由是每个直接用户回合的一次额外模型请求。对 Z.AI 官方端点使用其 [JSON 对象输出模式](https://docs.z.ai/api-reference/llm/chat-completion)；其他兼容端要求模型输出 JSON 并严格校验。路由输出只作为内部决策，不显示到对话，也不写入会话记录。每次到点续跑消息都属于 `SCHEDULED_TASK`，直接进入原 Agent 工具循环，避免把批准后的动作再次识别成新任务。

2026-09-28 起，意图路由只发送用户文字和相关文本上下文，不再提前上传图片；附件存在仅作为元数据。文字已完整指定时间和动作时照常路由；动作或时间依赖附件内容时，模型应返回 `continue`，由主 Agent 接收原始图片并理解，仍可调用 `demo_delay_propose`。普通执行主请求及其附件不变。该调整消除路由阶段重复发图，不取消原有意图判断，也不以关键词或正则代替模型分类。录制入口直接调用本地控制器，不经过此模型路由。

确认后，当前对话进入唯一的等待槽位。`1.8.0 / 121` 起确认态采用从底部滑入的全宽暖纸便签：用猫头鹰、“等你点头”、大字任务和自然时长明确请求用户决定，“取消 / 确认并开始”固定底部；完整任务可滚动，后台设置作为次要入口。等待态从顶部滑入，沿用暖纸/深色主题：突出剩余时间、进度、预计触发时间、最多两行的任务摘要和“停止任务”，已完成轮次作为次级信息；正常竖屏等待层无需滚动；短高度窗口先保留停止按钮空间，再允许正文滚动。上轮完整结果留在主对话。普通消息、历史切换及新建会话在等待期间被阻止，悬浮窗也不能排队普通消息；同一会话的整屏提醒控件事件仍可串行处理。离开页面或锁屏不会主动取消。到点后，进程级分发器向同一 `DemoConversation` 追加一条用户消息，使用同一个 `AgentSession` 和 `AgentRuntime` 启动普通 Tool/模型循环，并将结果写回该对话。等待和执行中都只占一个槽位。

周期任务的首次执行发生在确认后的第一个间隔；每轮 Agent 完成、结果写回原对话并释放运行槽位后，才开始下一轮完整间隔。例如设置 30 秒间隔、一次 Agent 运行耗时 15 秒，下一次执行约在该轮完成后 30 秒，而不是首次到点后 30 秒。不并发、不集中补跑。每一轮向控制器上报“有回答”或“未完成”两种结果：模型明确失败，或虽完成但没有任何回答内容，都算未完成；启动或结果保存失败同样立即停止。连续 3 轮未完成即自动停止并在对话中说明原因，任意一轮有回答则清零该计数。除这些条件外，周期任务由用户手动停止；配额的持续消耗与对话历史被“任务未完成”挤掉，正是给失败轮次设上限的原因。

确认定时任务只授权“稍后发起这个回合”，不等于授权到点后所有高影响工具；原有工具确认和“全授权”策略继续生效。后台没有 Activity 时，原有悬浮窗确认路径可承接需要用户决策的动作。

单次延时和周期间隔均限定在 1 秒至 24 小时；周期只支持固定间隔，不解析 Cron 表达式，除上文“连续 3 轮未完成自动停止”这一失败预算外没有其它自动结束条件（不支持指定执行次数或截止时间），也不创建 JobService、AlarmManager 触发器或独立 Agent 会话。该失败预算不持久化：进程重启本就按中断处理并停止周期。旧 SDK 模块仍保留供其他宿主使用，但 Demo 不注册 `agent_task_*` 工具。历史升级曾停止旧版仍处于 `SCHEDULED` 或 `RUNNING` 的后台任务并在关联对话说明；不会把旧任务悄悄迁成当前等待槽位。

## 进程与故障边界

`DemoDelayedTaskController` 与 `DemoAgentRunCoordinator` 由 `DemoProcessScope` 持有。Activity 只附着状态和展示弹窗；页面销毁不取消任务，悬浮窗的停止命令在没有 Activity 时仍能到达进程级控制器。App 引导用户在设备设置中允许自启动、后台运行并降低电池限制，但不把这些设置当成准点执行保证。

本地聊天历史按最近 100 条消息保留；若截断点落在助手回复之前，界面仍保留这条历史，但重建 `AgentSession` 时从第一条可用的用户消息开始，避免进程重启时因无效 transcript 崩溃。不清除或改写已保存的会话。

计时以 `SystemClock.elapsedRealtime()` 的截止时间为准；它包含设备深度休眠时间，但后台执行仍受 Android 与厂商的进程和电池策略约束。[Android SystemClock](https://developer.android.com/reference/android/os/SystemClock)、[后台优化](https://developer.android.com/topic/performance/background-optimization)。后台进程若暂时得不到执行时间，恢复后检查当前截止时间并尽快执行这一轮；该轮结束后才重新计时完整间隔。进程死亡会终止内存计时与 Agent 运行；本地只存一个中断标记，下次启动明确报告中断并停止后续周期，绝不自动补跑。用户按“停止任务”会取消等待或当前执行并在对话里记录。

## 接线与验收边界

2026-09-27 已验收补充：计时确认的“后台设置”改为打开共享的可选后台运行建议卡，提供电池/耗电、自启动设置及近期任务锁定说明。进入建议时临时收起确认卡，退出后按当前任务状态恢复；不会确认、取消或重置计时。设置页也可主动查看，“我已了解，不再提醒”仅保存建议阅读版本。最新完整包获用户反馈“可以了 测试通过”；建议页与设置往返的具体验证见 [权限与后台引导规范](demo-app-permission-guide.md)。本轮未重做真实模型计时链路或长期后台存活测试，不改变本文的进程存活和到点执行边界。

- `DemoModelIntentRouter`：每个直接用户回合的模型 JSON 路由；只按模型结构化结果选择单次/周期提案或继续原 Agent 流程。
- `DemoDelayAgentPlugin`：单次/周期提案工具、参数校验、首回合结束。
- `DemoDelayedTaskController`：唯一槽位、确认后计时、周期重装、取消和中断标记。
- `DemoDelayedMessageDispatcher`：到点后追加消息、启动同会话运行、保存结果。
- `DemoDelayedTaskDialog` / `MainActivity`：确认、倒计时、使用阻塞和重新附着。
- `DemoApplication` / Demo Manifest：清理旧任务并移除旧版后台组件入口。

`1.2.0 / 107` 的基本延时流程已获用户真机反馈“功能是可以的”；该反馈同时指出原系统弹窗与无限转圈过于简陋。`1.2.1 / 108` 的确认/等待卡片已在本地 Android 模拟器以浅色和深色分别渲染检查。真机后续诊断发现模型可能只回复“请确认”而不调用工具，导致没有提案及弹窗；`1.3.1 / 110` 曾加入宿主文字兜底，用户明确拒绝此设计，`1.3.2 / 111` 已改为模型路由。`1.6.0 / 115` 在同一单会话计时器上扩展固定间隔周期任务；用户真机测试发现 Agent 运行时间消耗了下一轮等待，`1.6.1 / 116` 将下一轮完整间隔改为从上轮结束后开始，用户随后反馈测试通过。`1.7.0 / 117` 区分顶部确认与底部等待两种界面；`1.7.1 / 118` 根据真机截图改为顶部全宽覆盖并收紧底部内容；`1.7.2 / 119` 的尝试在真机仍留灰条并叠加顶部空白；`1.7.3 / 120` 改用非浮动全屏透明窗口承载确认卡片。进程存活与准点执行边界未改变，不宣称系统级准点或后台存活保证。

在 `1.7.3 / 120` 本地保存点之后，按用户新的触达顺序调整为底部确认、顶部计时；顶部状态栏承托逻辑转由计时层使用。按钮点击先启动卡片退场，再处理计时状态；后台设置在退场完成后打开。底部卡片向下收回，顶部卡片向上收回，确认到等待的切换在旧层退场后显示新层。此项 UI 调整不改变计时状态机或授权语义。
